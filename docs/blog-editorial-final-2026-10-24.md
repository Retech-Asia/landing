## NEW POST: How to Scope an MVP With a Remote Development Team

- **Slug:** `how-to-scope-an-mvp-remote-development-team`
- **Canonical:** https://retech.asia/en/blog/how-to-scope-an-mvp-remote-development-team
- **Category:** Guides | **Author:** Retech Solutions | **Read time:** 4 min read
- **Date:** 2026-10-24
- **Cover image:** `/images/blog/how-to-scope-an-mvp-remote-development-team.webp` (1200x630, provenance in src/lib/blog-images.ts)
- **Excerpt / meta description:** Turn a product idea into a testable first release with user workflow, exclusions, acceptance criteria and a remote team decision rhythm.

### Full English content

**Lede:** An MVP is a first product that can test a meaningful assumption with real users. It is not a long feature list with every item marked “phase one,” and it is not a rough interface that cannot safely perform its central task. A remote team needs a written scope because small unstated assumptions can turn into days of implementation in the wrong direction.


### Name the decision the release should support

(id: `name-the-decision-the-release-should-support`, level 2, paras: 2)

Begin with one sentence: “We need to learn whether [user group] can [complete task] well enough to [business decision].” For an operations tool, the decision might be whether staff can replace a spreadsheet for a complete case, from intake through approval. For a marketplace, it might be whether users can discover an item, request it and receive a response. The sentence tells the team what should work end to end.

Identify one primary user and a second actor only if the core task cannot finish without them. Walk through a real example with the people who do the work. Capture starting data, action, exception and successful outcome. A workflow diagram or short annotated screen sequence is often more useful than a long list of abstract features.


### Split scope into three layers

(id: `split-scope-into-three-layers`, level 2, paras: 2)

The core path lets the primary user complete the task. The operating layer makes it usable responsibly: authentication, appropriate permissions, error states, logging, backup and support access as needed. The later layer contains enhancements that can wait without invalidating the test. A feature is not “later” if its absence makes the experiment unsafe or impossible.

For each candidate item ask: What question does it answer? What is the smallest implementation that answers it? What happens if we defer it? Keep a visible exclusions list. “No mobile app in the first release; responsive web supports the core workflow” is a useful scope boundary. “Everything else later” is not.


### Write acceptance criteria with examples

(id: `write-acceptance-criteria-with-examples`, level 2, paras: 2)

“User can create a project” is too broad. A testable criterion says which user may create it, required fields, uniqueness rule, what appears after save, and what happens on validation or network failure. Add one normal and one exception example. If an external system is involved, state which record is authoritative, expected sync timing, duplicate handling and behavior during an outage.

Ask the remote team to demonstrate the core path against these examples at each increment. Record decisions and changes in one shared place. The buyer should review a working build, not wait for a final reveal. Our [delivery process](/process) explains the artifacts and acceptance points.


### Estimate uncertainty explicitly

(id: `estimate-uncertainty-explicitly`, level 2, paras: 2)

Some work can be estimated from known screens and data rules. Other work depends on API access, sample data, regulatory review or user research. Split those uncertainties into a short discovery task with a concrete output: an integration spike, data audit, prototype or technical decision. An estimate should list assumptions, exclusions, third-party costs and who supplies credentials or content. A single confident deadline before those dependencies are known is not evidence of precision.

Agree how changes are handled. A new feature can replace another item in the same budget, move to a later phase, or increase scope. Keep the choice visible so the team does not quietly accumulate obligations.


### Run a small release review

(id: `run-a-small-release-review`, level 2, paras: 2)

Before launch, have a real user complete the task with realistic but safe data. Check permission boundaries, error recovery, analytics needed for the product question, and how support will see a problem. Decide in advance what evidence would justify continuing, changing direction or stopping. The MVP succeeds when it produces an informed decision, even if the first hypothesis proves wrong.

### Full English content

**Lede:** Hiring across the Pacific can work well when the work is clear enough to hand over and the people making decisions stay involved. It can also fail with a talented team if the buyer expects every question to be answered in the same working hour. The useful question is not simply whether Vietnam is cheaper. It is whether you can design a delivery relationship that gives engineers context, gives you visibility, and catches a wrong assumption before it becomes an expensive feature.


### Start with the job, not the team size

(id: `start-with-the-job-not-the-team-size`, level 2, paras: 2)

Write down the business workflow before asking for résumés. Who will use the system? What do they do today? What data is authoritative? Which integrations, permissions and approvals matter? For a custom CRM, for example, “manage leads” hides questions about ownership, duplicates, status changes, notifications and reporting. A partner can estimate a bounded first release much more reliably when those choices are visible.

Separate the first release from the eventual platform. Mark each requirement as essential for a user to complete one end-to-end task, necessary for safe operation, or later. Ask a prospective team to challenge the list and propose a small testable slice. Their questions reveal more about delivery ability than a generic technology pitch.


### Plan California–Vietnam overlap deliberately

(id: `plan-california-vietnam-overlap-deliberately`, level 2, paras: 2)

Vietnam uses UTC+7. California changes between daylight and standard time, so the offset changes during the year. ReTech already works with US West Coast overlap; its [follow-the-sun engineering guide](/blog/vietnam-timezone-follow-the-sun-engineering-202608) explains the operating context. Agree a recurring decision window that works in both seasons and use written updates for the rest. A practical pattern is a short meeting for blockers and decisions, a shared board for current work, and a demo at the end of each increment.

For every story, name the person who can answer a product question and the time by which an answer is needed. Record the decision in the ticket or specification. If a critical question is still open, the team should pause that slice and take the next independent item, not implement a guess. An asynchronous process can be an advantage when the handoff is disciplined; it is a liability when no one owns the handoff.


### Compare proposals on the same basis

(id: `compare-proposals-on-the-same-basis`, level 2, paras: 2)

Ask each candidate to explain the exact people and responsibilities they would assign: product analysis, design, engineering, review, QA, deployment and support. Request an example of an acceptance criterion, a working demo, and a sample handover artifact. If a case study is offered, establish the team's actual scope and whether the screenshots and outcomes have client permission.

Do not compare a single hourly figure with a fixed project price as if they covered the same work. Have the vendor separate discovery, implementation, testing, infrastructure, third-party software, model API usage, migration, training and post-launch support. A lower engineering rate can be offset by a broader scope, rework or more buyer-side coordination. Our [rates guide](/blog/vietnam-software-developer-rates-2026-complete-pricing-guide) explains how to ask for comparable total-cost assumptions without treating a public rate card as a quote.


### Put ownership and control in writing

(id: `put-ownership-and-control-in-writing`, level 2, paras: 2)

A cross-border agreement should identify deliverables, acceptance, change control, payment triggers, access, confidentiality, intellectual-property assignment or license, data handling, subcontracting, support and exit assistance. Decide which party owns repository accounts, cloud environments, domains and vendor subscriptions. Require a repeatable handover: source code, deployment instructions, credentials transferred safely, data model, operating notes and known issues.

These are commercial and legal decisions specific to your business. Have qualified advisers review applicable contracts, privacy and tax obligations; hiring a foreign vendor does not erase the buyer's obligations. A technical partner should be able to explain its practices and cooperate with that review without claiming to provide your legal advice.


### Use a paid, bounded first engagement

(id: `use-a-paid-bounded-first-engagement`, level 2, paras: 2)

A small discovery or first increment can test the relationship. Set a written output: a workflow map, a prioritized backlog, clickable flow or a narrow working feature with agreed acceptance tests. Review the artifact with actual users. Look for clear trade-offs, honest risk reporting and prompt correction when assumptions change. A successful pilot gives both sides a better basis for committing to a larger scope.

If you have a workflow in mind, [send us the current process and the first decision you need to make](/contact); we can discuss a bounded next step and a written estimate.

## NEW POST: Custom CRM vs Off-the-Shelf CRM: A Decision Guide for Growing Teams

- **Slug:** `custom-crm-vs-off-the-shelf-crm`
- **Canonical:** https://retech.asia/en/blog/custom-crm-vs-off-the-shelf-crm
- **Category:** Guides | **Author:** Retech Solutions | **Read time:** 4 min read
- **Date:** 2026-10-24
- **Cover image:** `/images/blog/custom-crm-vs-off-the-shelf-crm.webp` (1200x630, provenance in src/lib/blog-images.ts)
- **Excerpt / meta description:** Compare workflow fit, integration, data ownership and lifetime costs to decide when to configure a CRM and when a custom system is justified.

### Full English content

**Lede:** A CRM purchase is rarely a choice between “standard” and “unique.” Most teams need a familiar core: contacts, activities, a pipeline and reporting. Their differences appear in who can see a record, how a case advances, which external system is authoritative and what must happen when a deal closes. The best choice is the least complicated system that can support those differences without turning everyday work into a workaround.


### First, map the workflow you actually run

(id: `first-map-the-workflow-you-actually-run`, level 2, paras: 2)

Take one real customer record from first inquiry to completion. List its states, owners, required evidence, handoffs, approvals and exceptions. Mark where data comes from and where it must go. Ask users to show the spreadsheet, inbox or legacy screen they rely on when the current CRM cannot express a step. This exposes genuine requirements and habits that might be changed safely.

Then test a configured product against three representative cases: a normal path, a frequent exception and a permission-sensitive path. A vendor demonstration of the happy path is not enough. If configuration handles all three without fragile manual copying, start there.


### When an existing CRM is the sensible default

(id: `when-an-existing-crm-is-the-sensible-default`, level 2, paras: 2)

Choose an established product when your process resembles its standard model, its integrations cover your core systems, and your administrators can maintain the configuration. You gain a mature interface and common features without commissioning every basic function. Budget for seats, onboarding, configuration, migration, add-ons and ongoing administration. Verify export and API limits before committing.

Buying does not mean accepting the default setup. A well-configured CRM still needs data ownership, roles, duplicate rules, field definitions, reporting and staff training. If the team continues to keep a parallel spreadsheet, the project is not finished.


### When custom work earns its cost

(id: `when-custom-work-earns-its-cost`, level 2, paras: 2)

A custom CRM can make sense when the workflow is central to your service and repeated adaptations would make a packaged CRM hard to operate. Examples include unusual case relationships, complex permissions across internal and external users, specialist documents, or integrations that must enforce a consistent status across systems. The case is strongest when you can name the friction, the people affected and the operating decision the new system improves.

Custom software also creates responsibilities: product ownership, security review, testing, hosting, maintenance and a plan for changes. Avoid building a complete replacement on day one. Many teams should retain the existing CRM as the system of record and build a focused workflow beside it. An integration may solve the real problem at lower risk than migration.


### Compare lifetime costs, not headline prices

(id: `compare-lifetime-costs-not-headline-prices`, level 2, paras: 2)

Prepare a three-year scenario for each option. For a packaged CRM, include licenses as headcount grows, implementation, add-ons, integration work, admin time and exit costs. For custom work, include discovery, design, build, migration, infrastructure, support, change requests and internal product time. These are categories to calculate with your own quotes, not a universal savings claim.

Also compare failure modes. What happens if an API changes? Can you recover an accidentally deleted record? Is there a usable audit trail? Can a new employee understand the workflow? Who responds when the system is unavailable? A small proof using real but safely anonymized records often answers more than a feature checklist.


### A practical decision table

(id: `a-practical-decision-table`, level 2, paras: 2)

The answer can be hybrid: configure the CRM for contacts and sales while building a narrow operations layer around the hardest workflow. Write down the boundary and system of record before coding.

| Question | Configure an existing CRM | Consider focused custom work |
|---|---|---|
| Workflow | Standard pipeline with manageable exceptions | Core process cannot be represented without persistent workarounds |
| Integration | Supported connector and acceptable sync delay | Multiple systems require explicit ownership and reconciliation |
| Change | Admins can safely update fields and automation | Changes need domain-specific rules and engineering review |
| Data | Export, permissions and audit meet your needs | Relationships and access patterns need a different model |
| Team | Ready to administer the vendor product | Ready to own a product roadmap and support plan |

ReTech's [CRM systems service](/services/crm-systems) covers workflow design, permissions, integration and migration. If you need to distinguish a customer system from a content platform, see [CMS vs CRM](/blog/cms-vs-crm-choosing-right-system-business). [Share one troublesome workflow](/contact) and we can assess whether configuration, integration or a custom slice is justified.

### What a public rate can and cannot tell you

(id: `what-a-public-rate-can-and-cannot-tell-you`, level 2, paras: 2)

Directories such as [Clutch's Vietnam software developer listings](https://clutch.co/vn/developers) display company-reported hourly bands and minimum project sizes. Bands may refer to different roles, seniority, contract sizes and service inclusions. A salary survey describes employee compensation, not a client bill rate. A low-priced one-person assignment is not directly comparable with a vendor team responsible for QA, architecture and delivery management.

### Build a comparable cost sheet

(id: `build-a-comparable-cost-sheet`, level 2, paras: 2)

Ask each vendor to quote the same written scenario: user groups, first-release workflow, platforms, integrations, data migration, security needs, acceptance tests and expected support period. Then record:

For a time-and-materials proposal, calculate expected role hours × bill rates plus separately billed items. For a fixed scope, check assumptions and change-control terms. For a dedicated team, clarify what “one engineer per month” means for working time, leave, management, QA and replacement. Request a range for uncertain work and a plan to retire the uncertainty.

Fixed scope is useful when deliverables and acceptance can be described well. The contract should explain how an uncovered dependency or changed requirement is priced. A fixed number does not make unknown integrations disappear.

Ongoing engineering buys a team and delivery rhythm against a prioritized backlog. Agree on roles, capacity, review, access and ownership. It is a poor fit when no product owner can make timely decisions. (id: `compare-risk-and-delivered-value`, level 2, paras: 2)

Ask for a small sample of the vendor's real work and their exact role in it. Review the quality of questions, demo cadence, acceptance discipline and handover. A quote should state what is excluded as clearly as what is included. ### Full English content

**Lede:** An AI agent can read information, use tools and take several steps toward a goal. That makes it useful for some routine work and risky when its authority is vague. The practical starting point for a small business is one narrow process where the inputs, allowed actions and human decision are visible. “Automate the office” is not a testable brief.


### Pick a workflow with an observable finish line

(id: `pick-a-workflow-with-an-observable-finish-line`, level 2, paras: 2)

Consider inbound lead triage. A bounded agent might read a new inquiry, extract the service requested and urgency, check the CRM for an existing record, then prepare a summary and draft response for a staff member. It should not silently promise a price, change a customer's status or send a commitment. Another candidate is collecting invoice exceptions for a bookkeeper to review. In both cases, the agent reduces preparation work while a person owns the consequential decision.

Select a pilot by asking: does this task recur often, are the inputs available and lawful to use, is there a clear correct output, and can a person quickly review mistakes? If the answer to any is no, improve the workflow or data first. A simple deterministic rule can be better than an agent for a fixed mapping.


### Define the boundary before choosing a model

(id: `define-the-boundary-before-choosing-a-model`, level 2, paras: 3)

Write an action contract. List the records the agent may read, the fields it may change, the tools it may call, the actions that always need approval, and what happens when a tool times out or returns conflicting data. Give it the least access needed. Keep an audit log of inputs, tool calls, proposed changes, approvals and final outcome, subject to your retention and privacy policy.

For a lead example: reading an incoming message and existing contact is allowed; drafting a response is allowed; sending, deleting, issuing a refund or altering a signed contract requires a human or stays outside the pilot. Do not put sensitive customer information into a model service without checking the vendor terms, access controls and your own obligations.

[NIST's AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) distinguishes governance, mapping, measurement and management. For a small pilot, that translates into named ownership, a defined use case, an evaluation set and a process for correcting failures. It is a practical way to avoid treating a plausible answer as proof of reliability.


### Test on your own examples

(id: `test-on-your-own-examples`, level 2, paras: 2)

Collect a small set of past cases with permission and remove unnecessary personal data. Include normal, incomplete, duplicated and adversarial inputs. Decide in advance what counts as success: correct classification, no unauthorized action, useful draft, review time and cost per completed case. Compare the pilot with the current human process. Track false positives and the cases that need escalation, not just a single accuracy score.

Run in shadow mode first: the agent prepares output, a person performs the actual work, and the two are compared. Add limited write actions only after the team understands errors and rollback. Re-evaluate after changing models, prompts, tools or source data; those changes can alter behavior even when the user interface looks the same.


### Count the whole operating cost

(id: `count-the-whole-operating-cost`, level 2, paras: 2)

Model calls are one part of the budget. Include integration, monitoring, human review, retries, testing, data preparation and maintenance. A pilot is successful if it improves a named task at an acceptable error rate and total cost. If staff spend longer correcting drafts than preparing them, narrow the task or stop.

(id: `count-the-whole-operating-cost`, level 2, paras: 2)

Lệnh gọi model chỉ là một phần ngân sách. Hãy tính cả tích hợp, giám sát, xem xét của con người, retry, kiểm thử, chuẩn bị dữ liệu và bảo trì. Một thí điểm là thành công nếu nó cải thiện một nhiệm vụ được gọi tên ở mức tỷ lệ lỗi và tổng chi phí chấp nhận được. Nếu nhân viên mất nhiều thời gian hơn để sửa bản nháp so với tự soạn, hãy thu hẹp nhiệm vụ hoặc dừng lại.
